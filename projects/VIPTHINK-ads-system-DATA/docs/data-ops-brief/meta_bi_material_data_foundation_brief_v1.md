# 投放数据底座与 Meta-BI-素材匹配项目说明 v1

给数据运营 / 自动化投放系统 / 素材生产系统同事的下午对齐材料

生成日期：2026-05-19

## 一句话说明

这不是新增一张 BI 报表，也不是 AI 投放系统本身；这是要先把外部广告平台数据、内部后端转化数据、素材标签数据，在统一粒度和稳定主键下打通。只有底层数据能稳定 join，后续的自动周报、投放诊断、素材分析和 AI 投放系统才不会依赖人工命名和临时规则。

今天会议的目标不是现场定完整系统方案，也不是要求数据运营现场承诺开发排期。今天只确认：现有数据能不能支撑 FB 投放-后端转化-素材映射的 P0 数据闭环，以及缺口由谁补。

本次下午沟通只收敛一个 P0 问题：

> 以 FB/Meta 为样板，公司现在能不能产出一张以 `ad_id + date` 为核心粒度的投放-后端转化宽表，并同时建立 `ad_id -> creative_id -> material_id` 的素材映射关系？

如果不能，需要确认最低可支持粒度、缺哪些字段、由谁补、多久能补。

## 一、原始想法整理

1. 先推动数据运营提供目前公司投放数据字典。拿到以后，才能知道现有数据有什么、字段口径是什么、主键和关联键是什么、还缺什么。
2. 补数方向可以先分成三块：外部渠道投放数据、内部后端链路数据、素材数据。当前大目标还未完全收敛，所以底层要尽量保留可复用字段，但应用层不一定全部使用。
3. 最终不是靠下载多张 BI 报表再做人工匹配，而是在公司内部数据运营层面形成可复用的底层明细表或宽表。周报自动化也应该基于这些底层数据生成，而不是硬匹配现有 BI 报表和飞书周报。
4. 现有周报中的素材字段，例如“广告名称、素材类型、CPM、CTR、CVR、消耗、例子数、约课成本、ROI2”，有业务价值，但更像展示层字段，不能直接作为自动化投放系统 P0 数据源。

## 二、专业表达版本

### 1. 向数据运营要的不是“新报表”，而是当前投放数据资产说明

我希望先梳理公司现有投放数据资产，包括底层表、字段字典、字段口径、数据来源、更新频率、主键、关联键，以及目前 BI 报表是基于哪些 SQL 或宽表加工出来的。拿到现状以后，我们才能判断哪些数据已经具备系统化接入条件，哪些只是展示层字段，哪些需要补采或补建。

### 2. 三块数据需要分别治理

**外部渠道投放数据**：以 Meta/Facebook 为样板，尽量保留广告平台可拉取的原子字段，例如 `campaign`、`ad set`、`ad`、`creative`、`impression`、`click`、`spend`、`reach`、`frequency`、`objective`、`placement`、`date` 等。底层尽量完整，应用层按需取用。

**内部后端链路数据**：业务形态相对稳定，核心颗粒度应围绕“例子/lead”展开，保证例子、约课、到课、转化等事件能追溯到渠道、地区、日期，以及尽可能细的投放对象，如 `ad_id`、`adset_id`、`campaign_id`。

**素材数据**：这是目前最薄弱的一块。现在大量素材靠广告名称或素材名称承载信息，例如素材类型、语言、演员、尺寸、历史标签等，但缺少独立 `material_id`、结构化标签和稳定映射关系。因此短期只能靠命名解析和人工校验，长期必须建设素材管理和素材 ID 机制。

### 3. 数据运营层面的整合目标

在数据运营层面，目标不是把 BI 展示表继续拼起来，而是建立可复用的数据底座。可以先形成三类核心数据资产：

| 数据资产 | 推荐粒度/主键 | 作用 |
|---|---|---|
| 投放-后端转化事实表 | 优先 `ad_id + date`；降级 `adset_id + date`、`campaign_id + date` 或 `channel + date` | 把 Meta 投放表现和内部例子、约课、到课、转化、GMV 对齐 |
| 素材映射表 | `ad_id + creative_id + material_id` | 把平台广告对象、Meta 创意对象和公司内部素材资产打通 |
| 素材资产维表 | `material_id` | 管理素材类型、语言、题材、演员、尺寸、状态、历史标签等 |

## 三、ad_id / creative_id / material_id 的口径

这三个 ID 不能混用：

| ID | 中文理解 | 谁生成 | 代表什么 | 主要用途 |
|---|---|---|---|---|
| `ad_id` | 广告 ID | Meta | 一条具体广告投放实例 | 承接消耗、曝光、点击、例子、约课、ROI 等投放表现 |
| `creative_id` | Meta 创意 ID | Meta | 一条广告引用的创意配置对象 | 连接广告和创意内容，可能包含图片/视频、文案、标题、CTA、落地页等 |
| `material_id` | 内部素材 ID | 公司内部素材系统 | 一份可直接投放的成品素材资产 | 跨渠道、跨账户、跨广告复用同一个素材资产 |

推荐理解：

```text
campaign_id
  -> adset_id
    -> ad_id
      -> creative_id
        -> material_id
```

但这不是严格一对一关系：

- 一个 `ad_id` 在某个时间点通常引用一个 `creative_id`。
- 一个 `creative_id` 是 Meta 广告创意配置对象，不一定等于单个图片或视频文件。
- 同一个 `material_id` 可以在不同账户、不同广告、不同投放批次里对应多个 `creative_id`。
- 同一个 `material_id` 也可能被多个 `ad_id` 投放。

### P0 阶段对 material_id 的定义

P0 阶段不追求完美素材本体论，先采用可执行定义：

> `material_id` = 公司内部认定的一份“可直接投放的成品素材”。

如果字幕、时长、画面剪辑、语言版本发生变化，并且这些变化会影响投放表现分析，就应生成新的 `material_id`。未来如果需要把同一创意的不同版本归并，可以再增加 `parent_material_id` 或 `asset_variant_id`。

## 四、material_id 怎么和 ad_id / creative_id 对上

`ad_id` 和 `creative_id` 可以从 Meta 拉回来；`material_id` 是内部 ID，必须由公司内部生成和维护。不要把 Meta 当成内部素材主数据系统。

推荐三路匹配：

| 匹配方式 | 适用场景 | 可靠性 | 说明 |
|---|---|---:|---|
| 系统创建强匹配 | 自动投放系统创建广告 | 高 | 素材管理系统生成 `material_id`，投放系统创建 Meta creative/ad 后，直接保存 `material_id -> creative_id -> ad_id` |
| 命名解析中匹配 | 人工投放、过渡期 | 中 | 素材名、广告名或创意名中包含 `material_id`，从 `ad.name` 或 `creative.name` 解析 |
| 人工确认弱匹配 | 历史数据治理 | 低-中 | 用广告名称、素材类型、预览图、上传时间、账户等生成候选，再人工确认 |

### 不建议把 material_id 回传上去作为 P0 主方案

可以把 `material_id` 写进 Meta 的广告名、创意名、UTM 参数等可读字段，但这只能作为辅助和兜底，不应把 Meta 当成内部素材 ID 的权威系统。

原因：

- 命名可能被投放师改错、漏写、复制或截断。
- 不同渠道对名称长度和字符支持不一致。
- `video_id`、`image_hash` 等是 Meta 生成的外部资产线索，不是公司可定义的 `material_id`。
- 同一份内部素材在不同账户或不同上传批次里，可能产生不同 `video_id`、`image_hash` 或 `creative_id`。

### 推荐命名规则

如果未来素材都通过素材管理系统生成，建议素材文件名或广告/创意命名中带可解析的 `material_id`：

```text
MID_YYYYMMDD_0001_ActorA_Image_Topic_SegmentA
```

系统解析时只依赖前缀 ID：

```text
material_id = MID_YYYYMMDD_0001
```

后面的演员、形式、题材、地区标签只用于人读和辅助校验，不作为主键。

## 五、Meta API 里素材名可能出现在哪里

根据当前项目的 Meta readonly 读取设计，Meta 侧可读字段分两类：

**广告表现层 `insights_ad`**：

```text
ad_id
ad_name
spend
impressions
clicks
ctr
cpm
...
```

**广告对象层 `ads`**：

```text
id
name
campaign_id
adset_id
creative {
  id
  name
  title
  body
  thumbnail_url
  image_url
  video_id
  object_story_spec
}
```

例如 `YYYYMMDD_ActorA_Image_Topic_SegmentA` 这类名称，可能出现的位置是：

| 位置 | 字段 | 可能性 | 判断 |
|---|---|---:|---|
| 广告名称 | `ad.name` / `insights_ad.ad_name` | 高 | 你们 BI/周报里现在看到的“广告名称”大概率来自这里 |
| 创意名称 | `creative.name` | 中 | 如果创建 creative 时把素材名写成 creative name，就能读到 |
| 文案/标题 | `creative.title` / `creative.body` | 低 | 通常是广告展示文案，不适合放素材 ID |
| 视频对象 | `creative.video_id` | 可读但不适合 | 这是 Meta 视频对象 ID，不是公司可定义的 `material_id` |
| 创意配置 | `creative.object_story_spec` | 中 | 可能包含 video_data / link_data / image_hash 等配置，但不应作为内部素材主键 |

结论：

> `video_id` 可以作为外部素材线索，但不能作为 `material_id`。  
> 最稳设计是：创建广告时写映射；人工投放时从 `ad.name` 或 `creative.name` 解析 `material_id`；历史数据再人工确认。

## 六、今天和数据运营怎么对

1. 先说明目的：我们不是要新增一张 BI 报表，而是要确认自动化投放系统、素材分析和周报自动化能不能共用一套底层数据。
2. 请数据运营先交付当前投放数据字典：底层表、字段名、字段中文名、字段口径、来源、更新频率、主键、关联键、对应 BI 报表。
3. 以 FB 为 P0 样板，确认现有数据最低能做到什么粒度：`ad_id + date` 是否可行；如果不可行，是 `adset_id`、`campaign_id`，还是只能到渠道/日期。
4. 确认内部后端链路能否反查到投放维度：例子、约课、到课、转化这些事件能否关联到 `ad_id / adset_id / campaign_id`。
5. 单独讨论素材数据缺口：目前是否有 `ad_id`、`creative_id`、`material_id`、广告名称、素材名称、素材标签、素材状态之间的映射。
6. 确认 Meta 当前是否已经能拉到 `ad_id` 和 `creative_id`；如果 BI 底层已有这些字段，需要确认字段名和来源表。
7. 最后收敛出一个 P0 数据需求：先不治理全渠道和全历史，只验证 FB 的投放-后端转化宽表与素材映射表能否成立。

### 数据字典评审时不要只看“有没有字段”

数据字典评审重点不是字段列表，而是字段能不能成为系统契约。每个关键表和关键字段都需要确认：

| 检查项 | 需要确认什么 | 为什么重要 |
|---|---|---|
| 主键 | 每张底层表的主键是什么？是否唯一？ | 没有唯一性，开发无法稳定 join |
| 粒度 | `ad_id + date` 是否唯一？如果重复，重复维度是什么？ | 防止把地区、账户、归因窗口、总计行混在同一粒度 |
| 更新频率 | 表多久更新一次？每天几点可用？延迟多久？ | 决定周报、诊断和自动投放反馈能不能按时运行 |
| 历史范围 | 历史数据从哪天开始可用？是否有断档？ | 决定能否做趋势、复盘和素材历史表现 |
| 字段变更 | 字段口径或 SQL 改动由谁通知？ | 避免系统上线后被 BI SQL 变更破坏 |
| 样例数据 | 是否能给 100 行脱敏样例？ | 只看字段字典不够，必须看真实行结构 |
| 脏数据 | 是否有总计行、透视行、人工补录行？ | 防止把展示层数据接进系统事实表 |
| 派生公式 | `ROI2`、例子成本、约课成本、转化率是否有 SQL 公式？ | 开发不能猜公式，否则会和 BI 对不上 |
| 时区币种 | Meta 消耗、BI 消耗、GMV 的时区和币种是什么？ | ROI 和日报切分会受影响 |
| 归因窗口 | 例子、约课、到课、转化、GMV 按什么窗口归因？ | 避免把当日、当月、滚动窗口混用 |

## 七、给数据运营的直接需求文本

我这边想先把投放数据底座梳理清楚，不是让你们马上新增 BI 报表。现在我们后续会做自动化投放系统、素材分析和周报自动化，所以需要确认底层数据能不能稳定支撑。

第一步希望你们提供当前投放相关的数据字典或数据资产说明，包括：有哪些底层表和宽表、字段含义、字段口径、数据来源、更新频率、主键、关联键，以及目前 FB 投放 BI 报表是怎么从底层数据加工出来的。

我想先以 FB 为样板确认一件事：公司现在能不能产出一张以 `ad_id + date` 为核心粒度的投放-后端转化宽表？里面最好同时有 Meta 投放字段、内部例子/约课/到课/转化字段。如果现在做不到，最低能做到什么粒度，缺哪些字段？

素材这块也需要确认。Meta 侧我们希望拿到 `ad_id` 和 `creative_id`；内部侧希望建立 `material_id`。最终需要一张映射表把 `material_id -> creative_id -> ad_id` 对起来。未来素材管理系统可以把 `material_id` 写入素材名、广告名或创意名中，作为人工投放和历史数据的兜底解析方式，但 P0 最稳的是在创建广告或导入广告时直接写入映射表。

如果目前没有 `material_id`，我们先把当前仍在投放、仍有消耗、仍会影响决策的素材做初始化治理，不要求一次性治理全历史素材。

## 八、建议字段清单

| `account_id` | 广告账户 ID | Meta 稳定账户键 |
| `account_name` | 广告账户名称 | 展示字段，不能替代 ID |
| `campaign_id` | 广告计划 ID | Meta 稳定计划键 |
| `campaign_name` | 广告计划名称 | 展示字段 |
| `adset_id` | 广告组 ID | Meta 稳定广告组键 |
| `adset_name` | 广告组名称 | 展示字段 |
| `ad_id` | 广告 ID | P0 核心 join key |

| `creative_id` | Meta 创意 ID | 素材映射关键字段 |

## 九、分工边界

| 模块 | 负责什么 | 不负责什么 |
|---|---|---|
| 投放数据底座项目 | 字段字典、数据来源、粒度、主键、join 关系、数据运营需求、数据契约 | 不直接做投放策略、不直接做素材生产 |
| AI 投放系统 | 基于可信数据做诊断、建议、规则、自动化动作和效果回传 | 不应该自己猜字段口径，也不应该靠广告名称硬匹配 |
| 素材生产系统 | 管理素材资产、`material_id`、素材标签、素材版本、素材与广告/creative 的映射 | 不负责后端转化归因口径 |
| 周报自动化 | 基于底层事实表自动生成周报草稿和分析摘要 | 不应该继续依赖多张 BI 表和飞书周报的人工硬匹配 |

## 十、冷水提醒

不要把第一次对齐变成“全渠道、全历史、全素材、全自动化”的大工程。这样会让数据运营很难接，也很难承诺。

先用 FB 做样板，因为 FB 已经是当前治理和基建相对较好的渠道。把一个渠道跑通，再复制到其他渠道。

素材历史数据量很大，且命名不一定规范。P0 不建议一开始治理全部历史素材，可以先处理当前仍在投放、仍有消耗、仍会影响决策的素材。

不要把“素材名带 `material_id`”当成主系统设计。命名一定会被人改错、漏写、复制、截断，跨渠道也会变形。最稳顺序是：

```text
创建时写映射 > 名称解析 > 人工确认
```

如果只能靠名称解析，那素材分析第一版必须标注为“半自动、需人工校验”，不能承诺精确归因。

## 十一、建议今天只确认的 P0 问题

1. FB 当前是否能产出 `ad_id + date` 粒度的投放-后端转化宽表？
2. 如果不能，最低能做到什么粒度：`adset_id + date`、`campaign_id + date`，还是 `channel + region + date`？
3. Meta 侧是否已经能稳定拉到并入库 `ad_id` 和 `creative_id`？
4. BI 当前的“广告ID”是否稳定等于 Meta `ad_id`？
5. 当前是否有 `creative_id`、`material_id`、广告名称、素材名称、素材标签之间的映射？
6. 如果还没有 `material_id`，是否可以先对当前仍在投放且有消耗的素材做初始化编号？
7. 数据运营能否提供底层表名、字段字典、SQL owner、更新频率和 100 行脱敏样例？

## 十二、下午会议问题清单和沟通话术

这一节用于会议现场逐项确认。左边是要确认的问题，右边是可以直接对数据运营说的话。

### A. 会议目标对齐

| 要确认的问题 | 可以直接说的话 |
|---|---|
| 今天会议边界是什么？ | 今天我们不讨论完整系统怎么做，也不要求现场承诺开发排期。今天只想确认现有数据能不能支撑 FB 投放-后端转化-素材映射的 P0 数据闭环，以及缺口由谁补。 |
| 本次是不是只以 FB 为样板？ | 我建议先不铺全渠道，先用 FB 做样板。FB 跑通以后，再复制到其他渠道。 |
| 今天评审数据字典的标准是什么？ | 我们今天不只看有没有字段，还要看字段能不能作为系统契约：主键、粒度、唯一性、更新频率、归因窗口、负责人都要确认。 |

| 要确认的问题 | 可以直接说的话 |

## 附：join 的通俗解释

join 就是把两份数据按同一个稳定编号对上。例如 Meta 表里有 `ad_id`，内部转化表里也能记录 `ad_id`，那么就可以稳定知道某条广告带来了多少例子、约课、到课和转化。

反过来，如果两边只有“广告名称”或“素材名称”，那就只能靠名称猜。重名、改名、命名不规范都会导致匹配错误。

对于素材分析，推荐的 join 链路是：

```text
投放表现：date + ad_id
广告创意：ad_id -> creative_id
内部素材：creative_id/ad_id -> material_id
```

这条链路打通以后，才可以稳定回答：

- 哪个素材带来了有效例子？
- 同一个素材在不同广告组、不同地区、不同账户表现是否一致？
- 哪些素材只是 CTR 高，但后端转化差？
- 哪些素材值得复用、停投或改版？
